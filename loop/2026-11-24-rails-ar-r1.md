# Rails-2 round 1: a Module subclass instance is self in its own module_eval and its #initialize

**Why.** The first activerecord run (sqlite3 adapter, 427 files, the fw-gems install from main 86d0b3e8) stopped 128 files on the mere-ruby side before their tests ran. Two causes account for 108 of them, and both come from one gap. The gap is an instance of a `Module` subclass acting as the module it is.

- **103 files: enum.** `ActiveRecord::Enum` builds `EnumMethods < Module`, includes an instance, and calls the subclass's private `define_enum_methods` from inside the instance's `module_eval`. The body ran with the anonymous module behind the instance as self (`mod_inst_backing`), so `self.class` was `Module` and the helper was missing. Every test whose models declare an enum stopped at load.
- **5 files: has_secure_password.** `ActiveModel::SecurePassword::InstanceMethodsOnActivation#initialize` calls `attr_reader attribute`. It was "undefined method 'attr_reader' for an instance of", with or without `self.`, and through `send`. The literal statement form (`attr_reader :x`) defined nothing at all.

**The change.**

- **`mod_inst_self`.** `module_eval`, `class_eval`, `module_exec` and `instance_eval` on such an instance bind self to the instance (a `VObj`), not to its backing module. They pass the instance as the block argument too. Methods defined inside still land in the backing, as before.
- **`extend` and `include?`.** `extend` takes the instance, as `include` already did; it was "wrong argument type (expected Module)". `include?` answers for it.
- **`mod_inst_delegates`.** It now covers `attr`, `attr_reader`, `attr_writer` and `attr_accessor`. These four are left out of `modmeth` on purpose, because they change which arm answers a call; here they are named for the instance only.
- **The statement form.** `attr_reader :x` in a method whose self is such an instance defines on it, as the call form does.

**Corpus 960** covers the module_eval and exec forms, the self and class seen inside, `extend` and `include?` on the instance, a cut-down enum, and the six `attr_*` forms in an instance's `#initialize`. It matches ruby 4.0.9.

## Review of #192

- **Module's other methods (a regression).** Once self in the instance's `module_eval` was the instance, `alias_method`, `remove_method`, `undef_method` and `refine` there became NoMethodError. Rails' `undefine_attribute_methods` runs `module_eval { undef_method(*instance_methods) }` on a `GeneratedAttributeMethods < Module` instance, which touches about 57 activerecord files. `mod_inst_delegates` now sends Module's instance methods, public and private (`modpub`, `modpriv`), to the module the instance stands for, unless the subclass defines the name itself. Left with the object are identity and printing (`==`, `===`, `inspect`, `to_s`, `freeze`) and the hooks (`included`, `extended`, `method_added` and the rest).
- **A def under the VM (a regression).** With `MERE_RUBY_VM=1`, `vm_cls_stmt` defined into the module only when self was a `VClass`, so a `def` in the instance's `module_eval` landed on the subclass. It now maps self through `scope_mod_val` first, as the evaluator does. The evaluator had the same gap one level down. A `def` inside an expression in the body (`[(def m = 1)]`) goes through the statement evaluator, which read self and put it on the subclass. `register_class_blk` now sets the definee (`__definee_cls`) to the module when self is such an instance.
- **The statement form.** The `attr_*` statement in such an instance's method is dispatched as the call. The guard was the name `attr_reader` alone, so a subclass with its own `attr_reader` made `attr_accessor :w` define nothing. It is now "self is an instance of a Module subclass". The `VClass` arm and this one share `sattr_call`.
- **A frozen instance (review bot, P2).** The names sent on to the module (`attr_reader`, `alias_method`, `undef_method` and the rest) reached it although the instance was frozen; ruby raises FrozenError. Frozenness was checked on the module, and only the instance had it. Freezing such an instance now freezes its module too (`ofrozen_set`, and `mod_inst_backing` for a module made later). So every path that lands there is refused: a call, a `def` or `attr_reader` in its `module_eval`, a bare call in its own methods. `frz_cls_check` names the instance in the message, as ruby does ("can't modify frozen M: #<M:...>"). On main, the calls were refused only as unknown names, and a `def` in a frozen instance's `module_eval` went through.
- **Corpus 960** has each of these. It matches ruby with and without `MERE_RUBY_VM=1`, and the corpus was run both ways.
- **Left for a later round** (the same on main): the subclass's own `included` / `extended` are not called; `is_a?(m)` and `m === obj`; `M.new { }` with `super(&blk)`; `name` after the instance is assigned to a constant; `Module.nesting` in a string `module_eval`; `inspect` lists the instance's ivars.
