# Rails-2 round 3: a class is another class where ruby makes one (remove_const, and super from a class's #dup)

Two places where mere-ruby answered an existing class where ruby makes a new one. Together they are 45 of the 133 RED of Rails-2 round 3 (activerecord, sqlite3 adapter, main 30de57d4 with #225, ruby 4.0.10).

## A class defined again under a removed name is a new class (37)

After `Object.send(:remove_const, :Name)`, `class Name` makes a NEW class. The old one is still there for whoever holds it (its instances, a variable), and the new one has none of its methods, constants, mixins or superclass.

Rails' migrator loads a migration this way:

```ruby
Object.send(:remove_const, name) rescue nil
load(File.expand_path(filename))
name.constantize.new(name, version)
```

activerecord's migration_test defines, in the test file itself,

```ruby
class ValidPeopleHaveLastNames < ActiveRecord::Migration::Current
  def change
    drop_table :people
  end
end
```

to check that a name collision across directories is harmless. Here, `class ValidPeopleHaveLastNames` in the migration file reopened the old class, so its `#change` was still there and `migrator.up` dropped the `people` table.
The test that ran it failed, and so did the 36 tests after it in the file.

The tables key a class by its name, so a class could not simply be made again under the same key.
A removed name (`cls_removed`) now goes the way a Ruby::Box's new class already went: a new class under an internal name of its own, with the constant pointing at it and `Name` to show (`name_anon`), as `Name = Class.new` would do. The old class keeps its key and everything in it.
This is done in the three places a class statement defines a class: the top level, a nested `class` in a class body, and a nested `class X < expr`.

`remove_const` marks the name for any class or module it removes. It marked it only when the constant held the class keyed by that name, so a class defined again a second time (under an internal name) was not marked, and the next `class Name` reopened the first one.

Before, the top-level arm deleted the old class's constants and reopened it, keeping its methods. That deletion is gone: the new class has no constants because it is new.

Corpus 1057: methods, constants, mixins, class-level instance variables and singleton methods stay with the old class. The old instance keeps its class. The new class is reopened by its name. Another superclass is no mismatch. A superclass given by an expression works.
A module, and a class where a module was. A nested class written both ways. `#inherited` hears of the new class. Putting the old class back under the name reopens it. The migrator's remove-load-constantize loop, three times.

## super from a class's own #dup answers a copy (8)

```ruby
module ActiveRecord::Inheritance::ClassMethods
  def dup
    other = super
    other.set_base_class
    other
  end
end
```

`super` reached the class dispatch's `dup` / `clone` arm, which declines when the class's singleton has a method of that name. It did not read the mark that `super` sets to ask for the builtin (`skip9`, bi_skip), so the call fell through and answered the class itself:
`NumericData.dup.equal?(NumericData)` was true. numericality_validation_test builds throwaway models with `NumericData.dup`, so a validation added to the "copy" was added to NumericData and to every later copy. Eight tests failed on validations other tests had added.

The two arms (classes, and builtin modules) take `skip9` as well as "no method of its own". work2026-44 found the same answer from `Class.new { def self.dup = super }` while reviewing #221.

Corpus 1058 covers `Class.new { def self.dup = super }`, a module the class extends with #dup and #clone that call super, the copy's methods, the copy's own additions not reaching the original, two copies being two classes, a named copy, a module, and a class with no #dup of its own.
It also covers what a copy carries:

- A class's copy has its class methods, by #dup and by #clone alike. A class's singleton class is copied with it, and the copy's is another one.
- An ordinary object's #dup leaves its singleton methods behind and #clone keeps them.
- `clone(freeze: true)` and `clone(freeze: false)`, and #dup of a frozen class, which is not frozen. `clone(freeze: true)` of a class that is not frozen gave an unfrozen copy on main too (with or without a #clone of its own); the copy is frozen now, after its initialize_clone.

## migration_test now passes, and no longer fits in a round's 600 seconds

**In a round of the whole suite, migration_test will be WALL_LIMIT.** Its 37 RED are gone, but the file does not finish within the 600 s a file is given: the first 33 tests all passed, taking 15 s to 330 s each, and the run was stopped by hand at 4,786 s (max RSS 3,279 MB).
In round 3 the file had 30 MATCH and 37 RED. After this change its cases are not counted at all until the file gets faster.

**Where the time goes.** Not in the tests but in MigrationTest's teardown: 11 s to 20 s per test, against 0.15 s for ruby.
The teardown removes 14 columns that are not in `people` (`remove_column ... rescue nil`), and on sqlite every remove_column rebuilds the table through `alter_table`, about 72 SQL statements each.
A statement costs about 7 ms here and about 0.07 ms in ruby (`select 1` alone is 8 ms), so the teardown is around 1,000 statements at 100 times ruby's cost. With the logger turned off, the same 12 remove_column calls repeated 8 times take 8.5 s then about 7 s each round.
With it on, they take 12.8 s rising to 23 s. So about half of the cost, and the rise, are in writing each statement to `debug.log`. (The machine's load average was 31 to 49 during these runs; the ratios hold, the absolute numbers are high.)

**This was there on main too.** On main the first 11 tests take 10 s rising to 25 s. Then the 12th test drops `people` (the reopened class's `#change`), and the remaining 55 fail at once, so the file ended within 600 s.
This change does not make anything slower: loading the migrations again (remove_const and load, 12 times) takes 1.3 s each time and the removed classes are collected.

The cost of a statement is the next thing to work on, separately: the sqlite3 extension's path through the C API (prepare, step, building the result rows) and the logger.
