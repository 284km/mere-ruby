## A def in a Class.new block keeps the method's nesting (98)

`class A::B::C` has one lexical scope, C. A constant in its methods is looked up in C and then at the top level, not in A::B. A method's own body did that. A `def` inside a `Class.new { }` block that such a method runs captured the live nesting, which does not hold the method's while a method runs. The def's nesting was empty, and with none its constants were looked up through every enclosing namespace of the name.

`ActiveRecord::FixtureSet::RenderContext` is written that way on purpose ("has to be defined in compact style"). Its `binary` helper reads `File.binread`, and `File` was `ActiveRecord::FixtureSet::File`.

- **`register_class_blk`** sets the nesting to the method's (its frame's `__nest`) for a block written in a method, and puts it back, also when the body raises.
- **`native_definition_apply`** does the same. `Class.new { def b; end }` with a single def comes straight there.

## super from respond_to? is the builtin answer (96)

`super` from an object's own `respond_to?` answered "is there such a method at all": a private method was true, and `respond_to_missing?` was not asked. It is now `respond_to_answer`, the table form of `Kernel#respond_to?`, which does not ask the override again. A private or protected method answers only with include_all, and `respond_to_missing?` is asked with the flag given.

`ActiveRecord::Core` defines a private `to_ary` returning nil, so that `Array.wrap(record)` and `flatten` keep a record whole. Every record has ActiveModel's `respond_to?`, which calls super. So `Array.wrap(record)` saw true, called the private method, and got NoMethodError.
