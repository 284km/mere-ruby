# A source in another encoding runs on the VM

Of the corpus, four programs' main scripts fell back to the evaluator under MERE_RUBY_VM, and three of the four for one reason: "a source in Big5", "in Windows-31J", "in ISO-8859-7". The native compiler declined any source that is not UTF-8 or US-ASCII. This round removes that refusal, the first of the items between the VM and being the default (note 558, item 1).

## What the refusal was for

The Ruby compiler's entry for the VM says "its literals are the lexer's to read", and the native compiler said the same in its words (round 59), so that the Ruby one was not loaded to say it.

The native compiler does not need the lexer. It reads Prism's tree, and its literals already carry the source's encoding: a String's (`IvStr`), a Symbol's, a Regexp's, `__ENCODING__`. With the refusal behind a switch, the three programs ran on the VM, and two of the three matched ruby as they were.

## What differed, and the change

**A frozen literal's identity.** Under `# frozen_string_literal: true` in a Big5 source, `"abc".equal?("abc")` was false on the VM. ruby's frozen literal is its fstring: one object for every literal of that text in that encoding, wherever it is written. The loader interned a UTF-8 literal (by its text) and kept any other as the operand, one object for each place. It now interns the other too, under the key the evaluator uses (`str_fstring`).

**`"lit".freeze` and `-"lit"`.** These are instructions of their own (`opt_str_freeze`, `opt_str_uminus`), and the loader declined them in another encoding: "a String in another encoding". The VM runs them as the evaluator's expression for the same source, with the literal marked with its encoding as the evaluator's parser marks one. So a redefined `String#freeze` is still what `"lit".freeze` calls.

**What is declined in such a source is declined for good.** The Ruby compiler takes no such source, and asking it loads it, with Prism's Ruby library, to hear so (the cost round 59 found: a fifth of a Rails boot, for one BINARY file). A construct the native compiler declines in a source of another encoding is now answered as final, with the encoding in the reason.

## What the fallback was hiding

test_hash.rb is a US-ASCII source with a `"lit".freeze` in it, so the whole file ran on the evaluator under MERE_RUBY_VM, and passed. With the refusals gone it runs on the VM, and one test failed there:

```ruby
a = {"ABC" => :t}
b = {"ABC" => :t}
a.keys[0].equal?(b.keys[0])      # true; false on the VM
"ABC".freeze.equal?(a.keys[0])   # true; false on the VM
```

This was so on main for a UTF-8 source too. ruby compiles such a literal to `duphash`, a copy of a Hash made at compile time, and every String in that Hash is the fstring. The native compiler made the Hash's Strings frozen and each its own object. A String inside a literal Array or Hash is now interned as it is made (`ic_to_val`). Corpus 819 has the forms: a key, a value, an Array's elements, nested ones, a `case` over Strings, and a key that is not a literal.

A fallback is a file that passes because it is not run by what is being checked. Four programs of the corpus and this test file were that, and nothing asked anyone to look.

## Recorded: two gaps of the evaluator's lexer

Both are on main, on both executions, because the main script is read by the evaluator's parser before either runs it. Neither is the VM's, and neither is changed here. Corpus 818 is written around them.

**A Windows-31J or Shift_JIS character whose second byte is 0x5C**, a backslash (表, ソ, 能, 十 and others). The lexer reads that byte as an escape, in a String, a Symbol, a Regexp, a heredoc and a word list:

| in a `# coding: cp932` file | ruby | here |
|---|---|---|
| `p "表".bytes` | [149, 92] | SyntaxError |
| `p "表示".bytes` | [149, 92, 142, 166] | [149, 142, 166] |
| `p %w[表 a].map(&:bytes)` | [[149, 92], [97]] | [[149, 32, 97]] |

A required file with such a String or word list is right on the VM, where the native compiler takes the file whole and Prism has read it. One with such a Regexp literal is a SyntaxError on the VM too: the regexp engine's check of the literal reads the byte the same way. A main script is read by the evaluator's parser on either execution.

**Big5 and GBK characters have no known length.** `enc_db_ranges` knows EUC-KR and GB2312 only. So `?中`, `中 = 1` and `:中` are SyntaxErrors in a Big5 or a GBK source ("'@' without identifiers", when the second byte is in ASCII's range), where EUC-JP, Shift_JIS and EUC-KR sources read them. `"a\x81\x40b".valid_encoding?` is true in Big5, and false in ruby.
