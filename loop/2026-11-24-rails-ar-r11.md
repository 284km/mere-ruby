# Rails-2: extend takes its modules last first

**Why.** Three RED in activerecord's has_many_associations_test, on a build of main 0c435655:

```ruby
module NamedExtension;  def greeting = super + " :)"; end
module NamedExtension2; def greeting = "hullo"; end
has_many :comments_with_extend_2, extend: [NamedExtension, NamedExtension2], ...
post.comments_with_extend_2.greeting   # "hullo :)"; here "hullo"
```

The relation is extended with `extend(*modules)`.

**The cause.** `obj.extend(A, B)` takes its modules last first: `rb_obj_extend` counts its arguments down, so B is mixed in, then A, and A is the nearer one. They were taken first to last here, so B was the nearer and A's method was not reached at all. `include A, B` and `prepend A, B` were already right.

**The change.**

- `Kernel#extend` walks its arguments in reverse, for every kind of receiver that arm handles (an object, a class or module, a String, an Enumerator, main).
- The `extended` hooks run in that order too.
- When one of the modules defines `extend_object`, each module's `extend_object` and then its `extended` are called in turn, as `rb_obj_extend` calls them. They were all the `extend_object`s and then all the `extended`s.

**Corpus 973** has the shape with `super` between the two modules; one module at a time; three by a splat; `include` and `prepend` beside them; a module, a class, an Enumerator, a String and main as the receiver; `extend` with no argument; and the order of `extend_object` / `extended` for three modules, with and without an `extend_object` among them. It matches ruby 4.0.9 with and without `MERE_RUBY_VM=1`.

**On this build:** has_many_associations_test 321 cases, MATCH 316 → 319, RED 5 → 2. Max RSS 1,770 MB; the same file was 1,316 and 1,605 MB on two other builds of today, so its run-to-run variation is wide, and nothing in this change keeps anything.
