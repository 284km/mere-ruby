# A shareable constant's value that is not a literal is compiled

The last of the corpus's fallbacks under MERE_RUBY_VM: corpus 370, "a shareable_constant_value write of this is not compiled yet". Both compilers compiled such a write only when it was `X = a literal`. Any other form sent the whole file to the evaluator.

## What ruby compiles

The write is compiled as any constant write is. Its value is compiled by a rule of its own (`pm_compile_shareable_constant_value`):

- a literal (a number, a Symbol, a String, a Regexp, nil, true or false, and an Array or a Hash of those) is pushed already made shareable;
- an **Array or a Hash** that is not one is built of its elements, each by this same rule, and when it is the constant's own value it is made shareable: a send of `make_shareable`, or of `make_shareable_copy` under `experimental_copy`, to the VM's own object;
- **anything else** is compiled as it is. Under `literal` it is then checked: a send of `ensure_shareable` with the constant's path, whose failure is "cannot assign unshareable object to A::B". Under the other two settings it is made shareable when it is the constant's own value, and left as it is inside an Array or a Hash. An interpolated String gets a `-@` first.

So in `X += v`, `X ||= v` and `X &&= v` only `v` is the shareable value, and the operation is as it is.

The path is the constant's as written: `X`, `A::B`, `::X`, and `...::X` when the owner is not a constant. It is a US-ASCII String, the source's encoding when a name is not ASCII, and BINARY for the `...` form.

## The change

**Both compilers.** The Ruby compiler (`lib/iseq_compiler_ext.rb`, `shareable_value`) and the native one (`ic/`, `ic_shareable_value`) compile the eight kinds of constant write under a ShareableConstantNode: a plain write, `||=`, `&&=` and an operator, each bare or with an owner. The write goes the way it goes without the node, and its value is met on the way: the node compiler is told which node is the value, and compiles that one by the rule.

Two details are ruby's, and were found by comparing with it:
- the write's instructions carry the ShareableConstantNode's node id, not the write's;
- a literal Integer keeps its own instruction (`putobject_INT2FIX_1_`).

A Hash with a `**` in it is still declined, by both.

**The VM.** The three sends are to the VM's own object under names a program can spell (`make_shareable` is a method of Ractor too). The compilers mark them in the VM's export, and the VM runs them as what the evaluator's parser wraps the same value in: `Ractor.make_shareable`, and the two internal checks.

**The evaluator, where it differed from ruby.** With corpus 370 running on the VM, the two executions disagreed on forms 370 does not have, and ruby agreed with the VM:

| under a setting | ruby, and the VM | the evaluator |
|---|---|---|
| `X += [v]`, `A::X += [v]` | the result is not made shareable | made the result shareable |
| `# literal`, `X += [[1]]` | assigned | "cannot assign unshareable object to X" |
| `# literal`, `X &&= [2]` | `[2]`, shareable | raised the same error |
| `X ||= v` when X is set | nothing | "warning: already initialized constant X" |

The evaluator wrapped the whole of `X op v`. Its parser now marks the read of an op-assignment under a setting, and only the right side is wrapped.

## Numbers

Under MERE_RUBY_VM=1 no corpus program falls back: all 874 run on the VM. It was 31 when files first ran on the VM (round 38), 4 before round 62, and 1 after it.

The two compilers over the whole corpus: the Ruby compiler's tree is ruby's own for all 874 files, with none refused (one was); the native compiler's is the Ruby compiler's for 873, with 0 different and 1 it declines (a hash pattern's key, which the Ruby compiler takes).
