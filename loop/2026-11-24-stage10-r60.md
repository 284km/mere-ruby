# A required file the native compiler takes is not parsed by the evaluator's parser

Round 59 left the VM's Rails boot at 65.2 G instructions against the evaluator's 53.6 G, and named what was on top: the native compiler and the loader (12.3 G), and the evaluator's lexer and parser (4.8 G), whose statements the VM does not run. This round removes the second.

## The change

`do_require0` read every file with the evaluator's parser, and then asked the VM. For a file the VM takes, the parser's statements were made, kept for the length of the compile, and thrown away.

With MERE_RUBY_VM set, the VM is now asked first (`vm_file_first`), before the lexer reads the file. It answers the two statements that run the file's program, or nothing. On nothing, the file goes the way it went: parsed, then asked again through `vm_file_stmts`, which is where every refusal, error and warning is said.

The first ask takes a file only when all of these hold:
- the native compiler compiles all of it;
- Prism has no error and no warning of the source (the count is read from the serialized tree, `ic_tree_load`'s slot 6);
- every regexp literal in it parses and has no warning, checked as the parser's queue checks one (`rx_validate`, in `ic_to_val`);
- the loader takes every instruction;
- Coverage is not running, and MERE_RUBY_VM is `1` or `report`.

So a file with a syntax error, a warning, a BEGIN, a source in another encoding or a construct the native compiler declines is read by the evaluator's parser exactly as before, and says what it said.

## A defect in the long way, found by the corpus program

**A regexp literal that does not parse, in a required file.** `X = /(unclosed/` in a file that is required:
- on main it ended the program with "mere-ruby: regexp: invalid regular expression (StandardError)", which no `rescue SyntaxError` took;
- under MERE_RUBY_VM the Ruby compiler's own evals spent the parser's queue of literals to check, took the error for a refusal of theirs, and the file then ran with the broken literal.

The check now runs right after the parse and before any compile (`rxchk9`), and its failure is the file's SyntaxError, with the reason eval's has ("end pattern with unmatched parenthesis: /(unclosed/") and the file's path. The file is not loaded.

## How it was checked

A file that is not parsed by the evaluator's parser is a new path for everything that parser does on the side. The corpus runs each program as the main script, which this change does not touch. So every corpus program was also run as a **required file**: `ruby driver.rb program.rb`, where the driver is `require File.expand_path(ARGV.shift)`, on ruby 4.0.9, on the evaluator and on the VM.

| | programs |
|---|---|
| the same as ruby on both executions | 853 |
| different from ruby on both executions, the same way | 5 |
| different on the evaluator only | 1 |
| **different on the VM only** | **0** |

The six that differ do so on main's build too, run the same way: they are differences of the required form, not of this change (below). So is the one the evaluator alone has, corpus 527, which exits 1 there.

Corpus 816 is what the review of #215 asked to be held: what a required file says of itself. Its lines and file, `__method__`, `caller_locations`, where its methods, procs, lambdas, `define_method` bodies and attributes were written, a backtrace through it, `__END__`, a heredoc, its top-level locals, its `frozen_string_literal`, an `END` block, a top-level `return`; and a file with a warning, one that does not parse, and one whose regexp literal does not.
