# Regexp literals in any encoding on the VM, and Regexp.new's encoding for US-ASCII escapes and UTF-8 properties

Toward the VM as the default execution: the corpus programs that fall back to the evaluator, 10 before this round and 4 after.

## Regexp literals in another encoding

The loader refused two kinds of program, and sent them to the evaluator:
- a `putobject` of a Regexp in an encoding other than UTF-8 or US-ASCII (a BINARY `/\x80/n`, an EUC-JP `/../e`);
- a `toregexp` whose literal's flags name an encoding (n / u / e / s).

The refusal named corpus 462. Its folded `/#{%q"\x80"}/`, in a US-ASCII source, had come out UTF-8 on the VM. Both refusals are gone.

Six corpus programs now run on the VM and match ruby: 196, 339, 340, 365, 462, 464.

Two of them showed a difference in `Regexp.new`, on both executions. The VM's compiler folds an interpolated literal with only literal pieces into one Regexp made the way `Regexp.new` makes it:
- **A US-ASCII source with escapes of bytes past 0x7F** (`'\x80'`, `'a\xff'`, `'[\x80-\xff]'`) gave UTF-8, fixed. Ruby leaves it US-ASCII and not fixed; such escapes read as UTF-8 only in a UTF-8 string. `__rx_new` now keeps US-ASCII when the source is US-ASCII, its bytes are ASCII, it has no `\u`, and the escapes are all it has past ASCII.
- **A UTF-8 source that names a character property** (`'\p{Alpha}'`, `'\P{Alpha}'`, `'\p{^Alpha}'`) gave US-ASCII. Ruby fixes it to UTF-8. The rule that already did this for other ASCII-compatible encodings now covers UTF-8 too. A folded `/#{"\\p{Alpha}"}/` is corpus 365's.

**Left.**
- `Regexp.new('\p{Hiragana}'.force_encoding("US-ASCII"))` is a RegexpError in ruby ("invalid character property name"). Here it builds a pattern.
- The other four fallbacks are the three non-UTF-8 sources (corpus 261 in Big5, 447 in Windows-31J, 518 in ISO-8859-7) and corpus 370's `shareable_constant_value` write of a non-literal. Each runs on the evaluator and matches ruby.

## On #167's record: the default that ran twice was main's

The review of #167 asked whether a nil-valued block default ran twice on main, or only after round 96. On a build of main from before #167 (it has #161's `__tpcall`, not round 96's `tp_bstk`), on the evaluator:
- `$n = 0; def dn = ($n += 1; nil); proc { |a = dn| }.call; p $n` gives 2. Ruby gives 1.
  - `proc { |x, a = dn| }.call(1)` and `[1].each { |x, a = dn| }` give 2 as well.
  - A method's `def m(a = dn)` gives 1.
- `[proc { |a = 1| a }.call(nil), proc { |a, b = 2| b }.call(1, nil), lambda { |a = 3| a }.call(nil)]` gives `[1, 2, 3]`. Ruby gives `[nil, nil, nil]`.

The second result shows that the body's prologue ran on main and re-defaulted a nil. So the record of #167 stands: main had both. A default that returns something other than nil runs once on main, which may be what the review measured. Corpus 790 now checks that an explicit nil is kept.
