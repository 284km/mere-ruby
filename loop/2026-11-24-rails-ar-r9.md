# Rails-2: a define_method body keeps its method's block only when it can yield (a memory regression of #210)

**What went wrong.** #210 made a `yield` in a define_method body reach the block of the method the body was written in, for the receiver forms (`k.define_method(:m) { }`, `define_singleton_method`) and for the blocks of `Class.new` / `Module.new` / `Struct.new`. It kept the block in force for EVERY such body, with a yield in it or not. The kept block holds the calling method's frame, for as long as the defined method lives. Rails defines thousands of methods with `mod.define_method(name) { }` from methods that are called with a block.

**How it showed.** activerecord's nested_attributes_test, max RSS on the mere-ruby side:

| build | max RSS | state |
|---|---|---|
| before #210 (main 17a5db5f with #211) | 1,084 MB | COMPLETE |
| main 4981f346 (with #210) | 2,101 MB | MEMORY_LIMIT |
| main 4981f346 with `dm_capture_blk` switched off (a probe) | 996 MB | COMPLETE |
| this | 1,189 MB | COMPLETE |

What one defined method keeps, measured alone: 20,000 methods defined with a receiver on a class that stays, each from a method called with a block whose frame holds an 8 KB string.

| build | RSS added per method |
|---|---|
| with #210 | 16.0 to 16.7 KB |
| this | 4.5 KB |

**The change.**

- **`body_yields`** asks whether a body can reach its method's block: a `yield` anywhere in it that is not inside a `def`, also in a nested block or a lambda (`bare_yield_stmts`, the scan `blk_capture` already makes for a literal block), or a call of `eval` or `binding`, through which a yield the scan cannot read may run.
- **`dm_capture_blk`** and **`yblk_blk`** keep the block only for such a body.
- **`block_given?`** in a receiver-form body asks the frame it was written in, as the bare form's does: `dm_had_blk` is set for the two receiver forms. It is a flag, kept for every body. It answered false before this and before #210.

**Corpus 970** has, for each form, a call of the defining method with a block and without: a plain yield, one in a nested block, one in a lambda, `block_given?`, `binding.eval("block_given?")`, `defined?(yield)`, `Proc.new` (ArgumentError in ruby 4.0), and a body with no yield. It has the same name defined again from a call without a block, and 50 methods defined under one block. It matches ruby 4.0.9 with and without `MERE_RUBY_VM=1`. Corpus 967 still matches.

**On this build:** nested_attributes_test 170 cases, MATCH 164, 1,189 MB; migrator_test 35 of 35 (the cases #210 was for); autosave_association_test 217 of 217.

**Checked.** On main 4981f346 and this: `run_corpus.sh --both` 858/858, `MERE_RUBY_VM=1 run_corpus.sh --both` 858/858; the source gates (dead_defs, dup_defs, gc_roots, meth_writes, name_len, ns_names, bracket_depth); and tools/loop_rss_check.sh, nine of nine under 1.6.

**Why #210's checks missed it.** They were the migrator's tests and the corpus. Neither measures memory, and the migrator's file defines few methods. From here a fix for a cause is also run on one or two of the larger files, and their max RSS is compared with the build before it.

**Left.**

- **Under `MERE_RUBY_VM=1`,** a receiver-form body whose only way to the block is `eval("yield 7")` or `binding.eval("yield 8")` raises LocalJumpError. A body the VM compiled is opaque to the scan: it knows whether the program yields (`vm_yields`), not whether it calls eval. The evaluator runs it as ruby does. Before #210 it was LocalJumpError on both.
- **A defined method called with its own block.** `k.new.go { }` where the body yields: ruby yields to the block of the method the body was written in; here the call's block wins. The bare form has the same difference, from before #210.
- **`define_singleton_method` on a new object in a loop** grows about 3.5 times in tools/loop_rss_check.rb's measure, with or without a block in force, on main 86d0b3e8 too. It is not this regression, and it is why no case was added to that gate here.
