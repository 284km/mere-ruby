# What the VM's Rails boot was made of, and two parts of it removed

#209 measured the real Rails application on both executions and found the VM slower than the evaluator: booted again in the gem home a cold run left, 85.4 G instructions against 54.4 G, and 1.3 GB against 0.8 GB at the peak. This round takes that difference apart with a sample of each boot, taken to the process's end, and its instruction count.

## Where the 31 G went

Self time by function, the VM's less the evaluator's, the largest first:

| | G instructions | what it is |
|---|---|---|
| the Ruby compiler, loaded for one file | about 16 | below |
| string-keyed Map lookups, their hash and memcmp | 6.9 | much of it the Ruby compiler's own run |
| `__lang_scan_words`, `__lang_coro_scan_strings`, `__lang_pin_sort` | 5.9 | the collector reading the stopped stack's regions; below |
| region allocation and memmove | 3.9 | |
| the native compiler and the loader | about 3 | `ic_*`, `parser_lex`, `vm_load_seq` |

**One file brought in the Ruby compiler.** The native compiler declines a source that is not UTF-8 or US-ASCII, and answered nil for it. `vm_file_stmts` then asked the Ruby compiler, which says the same ("a source in ASCII-8BIT"), and the file ran on the evaluator. But asking loads the Ruby compiler and Prism's Ruby library, about 25,000 lines read by the evaluator. One BINARY file in the boot cost a fifth of it.

The native compiler now answers that refusal itself, in the Ruby compiler's words, and `vm_file_stmts` takes it as final, as it does a BEGIN.

**The parser's statements stayed until the file had run.** `do_require0` parses a file with the evaluator's parser first: its syntax errors, its warnings and its tables are the parser's. Then `vm_file_stmts` compiles the source for the VM and answers two statements that run the program. The parser's statements were not used again, but they were still reachable from the stack while the file ran, and so while every file it required ran.

A collection reads what the stopped stack points at. The boot has 12 or 13 collections, and one of them came while mail's `address_lists_parser.rb` was loading. That file is a generated parser made of tables. The collection walked 2.4 million nodes of its statements, 39 million words. On the evaluator the same statements are there too, but its collections fell elsewhere.

With MERE_RUBY_VM set, the parse and the compile now run inside one region (`REQP`). What leaves it is `vm_file_stmts`' answer:
- for a file the VM takes, the two statements, and the parser's statements go with the region;
- for a file the VM declines, the parse, copied out, which runs on the evaluator as before.

The parse itself is unchanged, so every error, warning and table it makes is as it was.

## What is left of the boot's difference

The VM's 65.2 G is the evaluator's 53.6 G with these on top, by inclusive samples:
- the native compiler, 10.1 G. Of that, 4 G is `ic_to_val`, which turns the compiled sequences into the Arrays `RubyVM::InstructionSequence#to_a` has;
- the loader, 2.2 G, which reads those Arrays back into the VM's tables;
- the evaluator's lexer and parser, 4.8 G, whose statements the VM does not run.

Two next steps follow from that, each a round of its own:
1. The native compiler writes the VM's tables directly, with no Arrays in between (about 6 G).
2. A file the native compiler takes is not parsed by the evaluator's parser at all (about 5 G). That needs the parser's side effects found and kept: its syntax errors and warnings, the regexp checks it queues, the lines it records for definitions.

With both, the VM's boot would be about the evaluator's.

## A defect found on the way: a shareable literal on the VM

`# shareable_constant_value: literal` and then `X = [1, [2, 3], {a: "s"}]` left `X` unfrozen on the VM: `X.frozen?` and `Ractor.shareable?(X)` were false. The evaluator and ruby freeze it. This was so on main, for the main script and for a required file.

Both compilers push such a literal with `putobject`, "already made shareable". The native compiler's value for an Array was left as an instruction's operand is, not frozen. Its values have a new form, `IvShr`, which is the same in `#to_a` and is frozen all the way down when it becomes a value. The Ruby compiler's value was already right.

## Also

`MERE_RUBY_VM=report` now names each file the native compiler declined, and why. That line is how the one BINARY file was found.

Corpus 815 requires files of each kind and checks what they leave: one the VM takes (a table, a proc over the file's locals, a method and where it was written, a nested require), a Windows-31J source, a file with a BEGIN, a shareable literal, a file that does not parse, and one whose parse warns.

**A note for whoever measures next.** #210, on main since, raised the memory of a Rails test file (reported by the Rails stream, with a fix on its way). Peak RSS measured on a main between the two is not comparable with the figures here.

**Left, from the Rails stream:** under MERE_RUBY_VM=1, a `define_method` body with a receiver that reaches its block only through `eval("yield 7")` or `binding.eval` raises LocalJumpError; the evaluator and ruby yield. Whether a body may yield is asked of its statements, and a VM body does not say whether it calls eval or binding. A mark for that in the program's record would close it.
