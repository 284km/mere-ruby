# Block events after the binding, define_method's events, and a bare call that finds self's method before a top-level def

Two rounds on branch stage10-r50 (2026-11-23), after #161.

## (96) a block's :b_call after its parameters are bound, and define_method's events (corpus 790)

The block side of (92), from the review of #161. Ruby fires a block's :b_call once its parameters are bound: after a default's own call (a lambda's, a keyword's), after the `#to_ary` a destructured `|(a, b)|` makes. Both executions fired it on the way in, before them. The evaluator also put a lambda's :b_call on the caller's line when the block had a default: its line came from the body's first statement, which is the defaults' prologue there.

- **The VM.** The loader now reads RUBY_EVENT_B_CALL. In a block's sequence, past its first instruction, it sets a new events bit, 32, and notes the program in vm_late_ids. vm_events then fires the :b_call there (vm_late_bcall), on that instruction's line: the block's `{` / `do`, as ruby marks it. run_block_tp leaves such a block's :b_call to it, and keeps the block as the hook's (tp_cur_blk) until then.
- **The evaluator.** run_block_tp no longer fires :b_call itself. It sets tp_bpend, and the run_block0_in it calls takes the flag before it binds anything, so a block a default runs takes only its own. Once the parameters are bound it runs the keywords' defaults (they are the body's prologue, defaults_prologue), fires the :b_call (tp_blk_fire_late), and runs the rest of the body. The line skips the prologue to the block's opening mark (tp_blk_info).
- **define_method.** Its body is a block, so on the VM its method's :call and its :b_call come after the defaults too. vm_late_bcall fires both for a define_method frame, and run_meth leaves both. On the VM its :b_return and :return are on the block's last line (vm_max_line); they were on its first.
- **define_method at the top level** went through call_method, which had no :b_call / :b_return for it at all, and returned on the caller's line. It now fires them as run_meth does, and marks the frame "__tpdm" for vm_late_bcall.
- **public_send** of a top-level method said "called for an instance of Object". public_send_guard now names main "main", as ruby does.

Corpus 790 has the cases. It differs on main's build on both executions.

**Left, and why.**
- **The evaluator's :b_return / :return line of a multi-line block** is the last line it ran, not the `}` / `end` (a define_method body's is its first line). The parser records no end line for a block. The VM has ruby's.
- **The evaluator's :return for a default that raises** (`def m3(a = raise("boom"))`): ruby fires :return with no :call; the evaluator fires neither. The VM matches ruby.
- **local_variables order** is not a TracePoint matter. Both executions put `**kw` and `&blk` first (`[:kw, :a, :b, :r, :k]`, ruby `[:a, :b, :r, :k, :kw]`), and the evaluator puts a destructured parameter's names before the parameters after it (`[:a, :b, :c]`, ruby `[:c, :a, :b]`). The binder writes those first, and the frame's order is the order of writing. It needs the parameters declared in ruby's local-table order before binding; that is its own round.

## (97) a bare call finds self's method before a top-level def (corpus 806)

`def foo = 7` at the top level and `class C; def foo = 9; def m = foo; end`: `C.new.m` was 7. A bare call with a top-level def of its name went to the top-level def (call_method) whatever self was: with no arguments (the EVar arm), with a block, and with arguments (ecall_args). A top-level def is a private method of Object, so ruby finds it only when nothing before Object in self's ancestors has the name.

The three arms now ask self_shadows_top first: self's class (an object's class, a class's singleton class), its ancestors through lookup_anc, and an owner other than Object, Kernel and BasicObject. When there is one, the call goes on to the arms below, which call it on self. Found while checking a define_method body's default, `define_method(:dm) { |a, b = dflt| }`, which called the top-level `dflt` and not the class's. The same on both executions.

lib/tempfile_ext.rb had leaned on the old order. Its replacement `create_anonymous` (a file kept under its name until it is closed) was written at the top level, after ruby's own in `class << Tempfile`. With the order fixed, Tempfile.create's bare call found ruby's: create-and-unlink, and `File.new(fd, path:)` answered an IO. It is now inside `class << Tempfile`, which replaces ruby's (corpus 526). m_pathname_lib.mere is regenerated.
